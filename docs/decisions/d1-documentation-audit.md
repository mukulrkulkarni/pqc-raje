2. **Offline-oriented delivery.** Documentation assets are local, the companion build has static integrity tests, and app requirements prohibit external requests.
3. **Evidence-rich implementation notes.** Chunks 1–2E separate current behavior, target behavior, tests, limits, and known omissions.
4. **Security-conscious routing.** `app/routes/docs.py` uses module and asset allow-lists, rejects missing targets, and constrains tutorial asset serving.

## Shortcomings and accuracy gaps

### Discoverability and onboarding

- No root README establishes prerequisites, supported Python version, installation command, launch commands, first successful CLI run, first successful web run, or documentation map.
- The getting-started page prioritizes legacy/general documentation and does not present the implemented four-step `/app` workflow.
- CLI and web onboarding are split across HTML, Markdown, requirements, and decision notes. A new user must infer the authoritative sequence.
- `website/site-config.json` labels `/app/index.html` as “App,” while the live application contract uses `/app/`; writers must distinguish static explanation from the running Flask route.

### Current versus target language

- `web-app-requirements.txt` contains both “current CLI” and “web target” descriptions. Chunks 2A–2E implemented much of that target, so direct reuse would incorrectly describe completed behavior as future behavior.
- `docs/decisions/web-app-design-meeting-report.md` still states “NO-GO for implementation” and lists pre-implementation gaps. It remains valid historical rationale, not current product guidance.
- Chunk notes accurately document serializers, runtime feasibility, cache/download behavior, and integration. They need consolidation and source-linked verification before publication.
- The requirements mention `.npz`; current workflow source and chunk notes document `.csv` and `.npy` acceptance. Public documentation must follow current executable behavior unless implementation changes are separately authorized.

### Setup, installation, use, and debugging journey

- Setup lacks one authoritative dependency/install path and an explicit offline verification step.
- Use lacks copyable end-to-end examples for both CLI and web using the same criteria and matrix.
- Output interpretation lacks one canonical explanation of raw net flow, ties, identifiers, top-ten display, and exact download formats.
- Debugging material is operator-focused but not indexed by user-visible symptoms such as malformed criteria, header mismatch, missing values, feasibility rejection, expired token, replaced result, or restart invalidation.
- Recovery expectations are distributed across cache notes and tests rather than a concise limitations/troubleshooting page.

### Duplication and maintenance

- Source HTML under `docs/modules/` is copied into nested website routes. This supports offline/static delivery but creates apparent duplicate ownership unless generated-file rules are explicit.
- Historical snapshots under `docs/design/**/snapshot/` intentionally duplicate module pages. Search results can mislead writers into citing stale snapshots.
- Requirements exist at root and in attachments. Writers need a declared authoritative source and must treat attachment copies as supplied context, not independently maintained truth.
- Module-level HTML, tutorial HTML, Markdown config documentation, design specifications, and review records overlap. The writer plan must assign one purpose to each format.

## Four-step onboarding mapping

The available supplied context defines: criteria entry → matrix entry → preview/validation → compute/results/downloads. Use it as the task spine, not as four separate disconnected tutorials.

1. **Prepare:** install locally, select CLI or web, understand constraints, and download/copy a minimal dataset.
2. **Provide inputs:** explain strict criteria and matrix contracts with positive and malformed examples.
3. **Review and run:** show mapping, validation, missing-value approval, feasibility, confirmation, and safe correction loops.
4. **Interpret and recover:** explain ranking, ties, canonical downloads, cache expiry/replacement/restart behavior, debugging, and evidence.

This mapping preserves the supplied four-step flow while adding setup and recovery around it. PI should confirm that this interpretation matches the unnamed template before drafting.

## Technical Document Writer structure plan recommendation

**Chosen:**
- Task spine plus reference layers — Minimizes duplication while serving first-run, operator, contributor, and scientific readers.

**Near-miss:**
- Module-first structure — Preserves current depth but leaves setup and web workflow fragmented.
- Separate CLI and web manuals — Clear channels but duplicates contracts, equations, limits, and troubleshooting.

**Disqualified:**
- Decision-log publication — Historical states conflict with current behavior.
- HTML-only authoring — Weak reviewability and source traceability.

### Proposed information architecture

1. **Root README (Markdown):** purpose, support boundary, prerequisites, installation, two launch paths, minimal success check, documentation map, offline statement.
2. **Getting started (Markdown source rendered to HTML/website):** one shared example, CLI path, web four-step path, expected outputs, next links.
3. **Web workflow guide:** criteria, matrix formats, preview, feasibility, compute, downloads, session/cache limits, recovery.
4. **CLI guide:** strict shared contract, current flags, identifiers, canonical outputs, non-interactive operation, equivalence with web.
5. **Concepts and scientific reference:** composition overview plus module tutorials; equations link to source and scientific tests.
6. **Operations and debugging:** local launch, dependency checks, failure catalogue, offline validation, cache/token behavior, performance model.
7. **Contributor verification:** test categories, focused commands, build/link checks, generated-file rules, traceability table.
8. **Limitations and security:** local-only boundary, single-worker scope, no app JavaScript, docs JavaScript distinction, data lifecycle, unsupported formats.

### Placement rules

- Author durable narrative and commands in Markdown when possible; generate HTML and website copies from one declared source.
- Keep interactive/visual module tutorials as self-contained HTML with local assets and a documented source-of-truth path.
- Treat `website/` as generated output; do not hand-edit generated pages unless the build contract explicitly says otherwise.
- Keep design snapshots and decision records outside user navigation and label them historical.
- Add route-safe links for served Flask pages and relative links for offline static pages; test both representations.

### Required review gates before drafting or layout changes

- PI approves the structure, authority map, and current-versus-target labels.

## Mandatory regression evidence for documentation stages

Each documentation stage must include executable positive and negative evidence where relevant:

- Missing targets: absent module/tutorial assets and invalid document names return controlled 404 responses.
- Malformed inputs: invalid JSON, schema failures, malformed CSV, unsupported files, bounds, NaN/Inf, and missing values.
- Keyboard interactions: browser-level traversal, visible focus, activation, skip/navigation order, and no keyboard trap.
- Math-renderer failure: app semantic math remains understandable without JavaScript; docs pages degrade intelligibly if local enhancement scripts fail.
- Local link integrity: Markdown links, generated static relative links, Flask route links, fragments, assets, and offline navigation.
