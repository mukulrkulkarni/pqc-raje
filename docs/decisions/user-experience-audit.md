# User experience audit

**Date:** 2026-10-27
**Reviewer:** UI/UX Redesign Agent
**Companion review:** Engineering Critic, `docs/decisions/architecture-repository-audit.md` (verdict: NEEDS WORK)
**Verdict:** **NEEDS WORK**
**Scope:** User stories and journeys for the CLI, `/app`, Getting Started, tutorials, runbooks, companion website, criteria cards, results/downloads, onboarding, errors/recovery, branding/layout/typography/spacing/navigation, semantic math, no-JS boundaries, and browser-deferred limitations.
**Excluded:** Application edits, documentation page edits, remote Git operations, browser/AT/zoom/reflow/keyboard/offline/load execution, commit.

## Executive conclusion

The no-JavaScript `/app` workflow (criteria → matrix → preview → compute → results) is coherent, accessible by static construction, and well tested: 503 focused tests pass locally (evidence below), covering step indicators, validation messaging, keyboard source assertions, and download integrity. Documentation surfaces (Getting Started, module tutorials, runbooks) share one consistent visual language and give users two converging task paths (CLI and web) that both land on the same committed example.

However, the release ships **two unconnected, contradictory UI systems under one app**: a legacy JSON-API flow (`/preview/<id>`, `/compute/start`, `app/templates/preview.html`, `config.html`) that bypasses the real validation adapter and is reachable only by direct HTTP call, and the current server-rendered no-JS flow (`/app/*`) that is the only one linked from any page. This is confusing for a maintainer reading the templates directory and is a latent trap for any future integrator who finds `/compute/start` and assumes it is the supported API. A second material finding is a **broken user journey at the CLI quickstart**: the documented copy-paste commands in `docs/tutorials/cli_quickstart.md` and `docs/GETTING_STARTED.html` disagree on expected output order for the identical committed example. A third finding is that the companion website and the Flask-served Getting Started page are near-duplicates maintained by hand in two places with already-diverging port/host assumptions, which the Engineering Critic also flagged structurally; this audit adds the user-facing symptom: a reader who lands on one page and then navigates to the other sees different anchor links and nav targets (`/docs/modules` vs `/modules/index.html`).

The release can remain **released with limitations**. Do not represent `/compute/start` and `/preview/<id>` as a supported integration surface, and do not claim the CLI quickstart commands are consistent across documents until the findings below are resolved.

## User stories and journeys

### 1. CLI: "run the committed example and get a ranking"

**Positive**

- `electre3/cli.py::main` implements a clear happy path: load criteria → load matrix → optional confirmation preview → compute → print top-10 or save `-o`. Error paths print to `stderr` and return nonzero (`electre3/cli.py` lines ~26–28, ~52–54), which is correct CLI convention.
- `docs/tutorials/cli_quickstart.md` documents the full data contract (identifier CSV shape, NumPy core shape, criteria JSON schema) before showing commands — a good "read before you run" structure.
- `-y`/`--yes` and `-q`/`--quiet` flags give a scriptable path alongside the interactive confirmation prompt (`cli.py` lines 29–34), serving both novice (sees preview, confirms) and automation (skips it) user stories.

**Negative (by design, confirmed correct)**

- Empty criteria, NaN/Inf thresholds, wrong matrix dimensionality, and mismatched array lengths are all rejected with specific `ValueError` messages tied to the failing field (`tests/test_negative.py`, all 20 cases pass under the 503-test run). This is good design: errors name the broken input rather than failing generically.

**Edge / contradiction (negative finding)**

- `docs/tutorials/cli_quickstart.md` states: "Expected output is `B`, then `A`, then `C`" for `python -m electre3.cli examples/assets_priority/matrix_with_headers.csv examples/assets_priority/criteria.json -y` (direct CSV run, identifiers preserved).
- `docs/GETTING_STARTED.html` (`#cli` section) instead walks the **converter** path (`scripts/convert_matrix_csv.py` → `.npy` → CLI) and states: "Expected converted-NumPy ranking lines: `1. 1` / `2. 0` / `3. 2`" — i.e., positional order `1, 0, 2`.
- `website/index.html` (`#cli` section) shows a third phrasing for the same converter path: "its numeric NumPy output uses positional identifiers `1`, `0`, and `2`" inline in prose rather than as a labeled output block.
- These are not necessarily mathematically inconsistent (direct-CSV vs. converted-NumPy can legitimately print different label schemes for the same ranking, since NumPy assigns positional IDs `0..N-1` while CSV preserves source IDs), but **no single document shows both paths side-by-side with one explanation of why the printed labels differ**. A first-time user who runs the CLI quickstart's direct-CSV command, sees `B, A, C`, then opens Getting Started and sees `1, 0, 2` for "the same committed scenario" has a reasonable, uncorrected impression that something is broken or inconsistent. This is a **documentation-journey defect**, not a computation defect — but it directly damages first-run trust, which is the single highest-value moment in a CLI tool's user experience.
- **Priority: P1.** Add one cross-reference sentence in both `docs/GETTING_STARTED.html` and `docs/tutorials/cli_quickstart.md` explicitly stating "direct CSV preserves source identifiers (`B, A, C`); the NumPy-converter path assigns positional identifiers to the same ranking order (`1, 0, 2`) — same ranking, different labels." (Documentation-only change; out of scope for this audit to perform, in scope to flag.)

### 2. `/app` no-JS web workflow: "define criteria → provide matrix → confirm → see ranking → download"

**Positive**

- Four-step journey is explicit and consistent: every template literally states `Step N of 4` (`app_input.html` "Step 1 of 4", `app_matrix.html` "Step 2 of 4", `app_preview.html` "Step 3 of 4", `app_results.html` "Step 4 of 4"). This is a textbook wizard pattern and gives users a clear sense of progress without JavaScript.
- Criteria entry supports two mental models: paste raw JSON for power users, or a structured "criteria card" grid for first-time users (`app_input.html`, `fieldset.criteria-mode`). Radio-button mode selection with `checked` state preserved on validation error (`{% if not submitted or submitted.get('criteria_mode') == 'json' %}`) avoids re-entry pain on error — confirmed executed in `test_app_workflow.py::test_rejects_out_of_range_scores_and_invalid_criteria`.
- The criteria-card UI (`app_input.html`, `.criteria-card` in `style.css`) uses a checkbox-driven `:checked ~ selector` pattern to visually highlight included cards *without JavaScript* — a well-executed CSS-only interaction (`style.css` lines ~245–260, `.include-toggle:checked ~ .criteria-card-surface`). It includes a visible `Included`/`Not included` text badge (not just color), satisfying a non-color-only state cue.
- Error recovery is in-context: `app_input.html` and `app_matrix.html` both render `{% if error %}<p role="alert">...{% endif %}` at the top of the same form the user just submitted, with `submitted` values preserved for re-editing (`workflow.py::confirm_inputs`, `preview`). Confirmed executed: `test_app_workflow.py::test_preview_reports_header_and_missing_value_errors`.
- The compute step requires an explicit confirmation checkbox (`app_preview.html`: `<input type="checkbox" name="confirm_compute" value="yes" required>`) layered on top of a required preview step, giving a deliberate "review before you commit expensive computation" story. Confirmed executed: `test_app_workflow.py::test_compute_requires_preview_and_confirmation`.
- Results page gives three clear exits: download canonical JSON, start another ranking, or (implicitly) stay to read the table — `app_results.html`.
- Download security/UX is strong: checksum-verified cache, rate-limiting (429), expiry (404), and a `Cache-Control: no-store` header so a shared machine does not leak a prior user's results (`workflow.py::download_result`, confirmed by `test_app_workflow.py::test_download_serves_exact_cached_bytes_with_safe_headers`).
- Timeout and infeasibility paths explicitly avoid publishing a misleading partial result or a dead download link (`workflow.py::compute`, `test_compute_timeout_returns_no_partial_result_or_download` — confirmed passing).

**Negative (correctly rejecting bad input)**

- CSV header/criteria mismatch, missing score cells without opt-in replacement, and out-of-range `[0,1]` scores are all rejected with field-specific messages, confirmed by `test_app_workflow.py::test_preview_reports_header_and_missing_value_errors` and `test_rejects_out_of_range_scores_and_invalid_criteria`.
- Fewer than 2 structured criteria cards selected is rejected server-side (`workflow.py::_criteria_from_form`, "Select at least 2 criteria in the structured form.").

**Edge**

- `_criteria_from_form` silently ignores "all values from omitted cards, including malformed edited values" (comment in `workflow.py`). This is a deliberate, documented trade-off: a user who fills in a bogus value in a card they forgot to check will not be warned that their edit was discarded. This is a minor silent-data-loss risk for a distracted user, not a crash risk.
- The structured-criteria form always ships default placeholder values (`weight=0.125`, `q=p=v=0`), which are only valid together if the user deliberately adjusts thresholds; a user who checks a card and submits immediately without editing values will get a technically valid but probably meaningless `q=p=v=0` criterion. No inline warning nudges them to adjust thresholds before submit.

**Negative finding — orphaned, contradictory parallel UI**

- `app/routes/preview.py` and `app/routes/compute.py` implement a *second*, JSON-API-based upload/confirm/compute workflow (`/preview/<upload_id>`, `/preview/<upload_id>/confirm`, `/compute/start`) with its own templates (`preview.html`, `config.html`) and its own confirmation-gate semantics (session-stored `confirmed_uploads` list vs. the `/app` flow's per-workflow state dict). These routes are registered in `app/__init__.py` alongside the real `/app` blueprint and are **not linked from any page** in `/app`, Getting Started, or the website. The only "documentation" of their existence is an inline code comment and one compatibility-preserving negative test (`tests/test_app_workflow.py::test_download_rejects_unknown_token_and_preserves_compatibility_routes`, which labels `/compute/start` a "compatibility route").
- `docs/runbook/debugging.md` §1 ("Upload not confirmed" HTTP 403) documents **only** this orphaned flow's error code (`POST /compute/start` → 403, fix via `POST /preview/<upload_id>/confirm`) and never mentions the real `/app` workflow's analogous gate (the `confirm_compute` checkbox in `app_preview.html`, which 400s rather than 403s). A maintainer debugging a real `/app` user's stuck session using this runbook entry will look for the wrong route and the wrong status code.
- This is a genuine UX/maintainability hazard: two different session-state shapes, two different confirmation semantics, two different status codes for "you skipped a step" (403 vs 400), and zero user-facing navigation path to the legacy one. It is good that it is inert, but it is undocumented as dead code, which is worse than deleting it or clearly labeling it.
- **Priority: P0 (documentation-of-architecture gap, not a runtime defect).** Either (a) mark `preview.py`/`compute.py`/`preview.html`/`config.html` explicitly as a deprecated/legacy compatibility surface in a code comment and in `docs/runbook/debugging.md`, correcting §1 to describe the real `/app` gate, or (b) remove them in a future, separately approved implementation chunk. This audit performs neither; it flags the finding for PI/maintainer decision, since implementation/page edits are out of scope here.

### 3. Getting Started: "land once, pick CLI or web, get oriented"

**Positive**

- Single entry point (`/` → `docs/GETTING_STARTED.html` via `app/routes/docs.py::landing`) presents exactly three choices (CLI, Local web app, Reference) as parallel cards, each with one clear next action — good reduction of initial decision paralysis.
- The page is explicit about its own limitations in the user's language, not just internally: "The app serves HTML without JavaScript... Browser reflow, browser zoom, keyboard, offline, and screen-reader evidence remain unverified as documented." This is honest, in-context expectation-setting rather than a buried disclaimer — a strong practice for a pre-release artifact.
- A visible `aside.note` ("Documentation status: Phase 1 content remains under D3 review. It is not a release claim.") keeps the reader from over-trusting draft content, confirmed present and tested by `tests/test_d3_phase1_docs.py` (not re-run in this audit's focused set, but referenced by the architecture audit's broader 481-test run).

**Negative / edge**

- See CLI finding above: the Getting Started CLI section and the standalone `cli_quickstart.md` tutorial describe different (though not necessarily wrong) command paths for "the CLI task," which can read as contradictory to a user who checks both.
- The nav bar in `docs/GETTING_STARTED.html` (`<a href="/" aria-current="page">`, `/app`, `/docs/modules`) uses **Flask route paths**, while the structurally near-identical `website/index.html` nav bar uses **static file paths** (`/index.html`, `/app/index.html`, `/modules/index.html`). A user who is served the Flask-rendered Getting Started page and later opens the static-built companion website (e.g., via `file://` or a static host) will see different link shapes for conceptually the same destinations. This is consistent with the Engineering Critic's structural finding that generated website content and Flask-served docs are not unified by one manifest; the user-facing symptom is that identical-looking nav bars silently point to different URL schemes depending on which surface served the page.

### 4. Module tutorials / criteria cards (`/docs/modules`) and companion website

**Positive**

- The module index (`docs/modules/index.html`) and individual tutorials share one consistent navigation contract across all five modules (config, validate, block, accumulator, ranking) — confirmed by `tests/test_docs_routes.py::TestAllowListEnforcement` (passing) and the generated primary-nav CSS class shared across tutorial pages (`.primary-nav`, seen in `ranking_tutorial_side_by_side.html`).
- Dark/light/system theme toggle (`data-theme`, `.seg[role=group]`) is implemented with visible `aria-pressed` state and a documented `localStorage` failure fallback (`try`/`catch`), confirmed by `tests/test_docs_routes.py::TestThemeScriptSelection::test_theme_js_handles_localstorage_failure` (passing). This correctly treats "no persistent storage" as a recoverable, non-blocking condition rather than a hard failure.
- Interactive code-row selection (`highlight.js`) is layered as **progressive enhancement over a working `:target` CSS fallback** (`.row:target` rules present in `ranking_tutorial_side_by_side.html`), so the keyboard/no-JS user retains core navigation (jump to a numbered code range) even if script execution fails or is blocked, consistent with the app's zero-script CSP on `/app` routes and the docs route's permissive-but-local CSP (`script-src 'self'`).
- Keyboard operability is unusually thorough for a documentation page: `tests/test_docs_routes.py::TestKeyboardOperability` statically confirms Enter/Space handling, `preventDefault` on Space (to stop page scroll), `aria-pressed` toggling, and a no-throw guard when an expected DOM element is missing — all passing in this audit's run.
- Usage examples are explicitly marked illustrative and warn against treating sample numeric output as expected results (`tests/test_docs_routes.py::TestTutorialContent::test_usage_example_marked_illustrative`, passing) — this is good practice against a common MCDA documentation failure mode (readers copy example numbers as if they were universal answers).

**Negative / edge**

- `test_highlight_js_has_debug_mode` confirms a `?debug=1` query parameter triggers `console.log` output in production-served `highlight.js`. This is low-risk (client-side, no data exposure) but is an intentional debug surface shipped to end users; it should be noted, not necessarily removed, since no sensitive data is logged per the reviewed source excerpt.
- Semantic math is implemented as HTML entities and `<sup>`/`<sub>` (e.g., `&phi;<sup>+</sup>`, `&Sigma;`, `&times;`), not MathJax/KaTeX. This is **consistent with the Engineering Critic's note** that "math-renderer failure has no regression" because no such renderer exists in the shipped path. From a UX lens this is a reasonable, honest trade-off for a no-JS, offline-first, CSP-strict release: semantic HTML entities render instantly, requires no network fetch, and cannot fail to load — at the cost of less visually polished typesetting than a dedicated math renderer. No action required; this audit confirms the choice is coherent with the no-JS/offline goals rather than an oversight.

### 5. Branding, layout, typography, spacing, navigation consistency

**Positive**

- A shared design-token vocabulary (`--color-primary: #6400ff`, `--color-accent: #7eddd3`, `--font-sans: Arial, sans-serif`, `--space-xs` through `--space-xl`/`--space-2xl`, 4px/8px radius scale) appears, in slightly different concrete forms, across `app/static/style.css`, `docs/GETTING_STARTED.html`, `website/index.html`, `website/app/index.html`, and `docs/modules/index.html`. The same purple/aqua accent pairing and Arial-based type scale give the product one recognizable identity across CLI docs, the companion website, and the live app.
- Responsive behavior is handled consistently: `app/static/style.css` collapses the criteria-card grid from 4 → 2 → 1 columns at 900px/520px breakpoints and converts data tables to a label-prefixed stacked layout under 768px using the standard `data-label` + `::before` technique — a correct, broadly compatible responsive-table pattern that does not depend on JavaScript.
- Focus-visible styling is applied consistently with the brand accent color across `/app` forms (`input:focus, select:focus, textarea:focus, button:focus { outline: 3px solid var(--color-accent); }`) and tutorial pages (`:focus-visible { ... var(--accent) ... }`, enforced by `tests/test_docs_routes.py::test_focus_visible_uses_accent_outline`), giving one coherent, on-brand focus affordance everywhere a keyboard user would look for it. This is a **positive, non-visual accessibility signal** worth highlighting even though full keyboard-execution evidence remains browser-deferred.

**Negative / edge**

- The design tokens are **copy-pasted per page, not shared from one source file**. `app/static/style.css` is a real linked stylesheet; every HTML page under `docs/` and `website/` instead inlines its own `<style>` block with its own copy of the token list, each one hand-maintained. Engineering Critic's audit already flags the structural risk (no single manifest, no determinism test on rebuild); the UX-facing symptom is observable today: `docs/GETTING_STARTED.html` defines `--space-2xl` and `clamp(2rem,5vw,3.2rem)` hero type scaling that `app/static/style.css` does not define at all (the `/app` workflow pages have no hero section and a flatter `h1 { font-size: 2rem }` rule), so the visual "voice" of the marketing/docs pages and the task-focused app pages is deliberately different in scale but identically branded in color — a reasonable content-type-driven choice, but currently achieved by duplication rather than a shared base token file plus page-specific overrides.
- `docs/modules/ranking_tutorial_side_by_side.html` and `docs/modules/index.html` use a materially different, denser token set (`--s1` through `--s6` in 4–32px steps, `--sidebar-w`, `--code-frac`) than the `--space-xs`…`--space-xl` scale used by `/app` and Getting Started. Both scales are internally consistent and well-tested (`tests/test_docs_routes.py::TestLayout2Parity` enforces the tutorial's own token contract), but a user moving from Getting Started to a module tutorial experiences a layout-density shift (sidebar-based code-walkthrough vs. hero-card landing) that is not sign-posted anywhere as an intentional change of mode. This is a low-severity but real continuity gap.
- Primary navigation differs in presence and shape across surfaces: `/app` workflow pages (`app_input.html`, `app_matrix.html`, etc.) have **no persistent navigation bar at all** — the only way back to Getting Started from deep in the 4-step wizard is the browser Back button or the final results page's "Start another ranking" link. By contrast, Getting Started, the website, and module tutorials all carry a `nav.nav`/`.primary-nav` bar with Getting Started/App/Tutorials links. A user who starts the `/app` wizard, wants to bail out to read a tutorial mid-flow, and does not know to use Back has no visible escape hatch.
  - **Priority: P1.** Add a minimal, no-JS-safe navigation link (e.g., "Exit to Getting Started") to the `/app` wizard templates in a future, separately approved documentation/implementation chunk. Not performed here; application template edits are out of scope for this audit.

### 6. Onboarding and errors/recovery (cross-cutting)

**Positive**

- Every validation error observed across `/app` (`app_input.html`, `app_matrix.html`) and the CLI (`cli.py`) names the specific offending field or rule rather than a generic failure, consistent with `docs/runbook/debugging.md`'s "golden rule" of treating every change as a contract change and the shared validator's descriptive `ValueError` messages (`electre3/shared.py`, confirmed via `tests/test_app_workflow.py` and `tests/test_negative.py`).
- The missing-score-cell recovery path is a genuine piece of good UX: rather than forcing the user to fix the source file, `app_matrix.html` offers an in-page opt-in ("I approve replacement of missing score cells") with a bounded, visible numeric default (`0`–`1`), and the preview step lets the user see exactly where that replacement was applied, confirmed by `test_app_workflow.py::test_missing_value_approval_replaces_with_default_zero`.
- Infeasibility and timeout are treated as first-class, clearly worded outcomes (`422`/`504` with human-readable messages), not swallowed into a generic `500`, and are proven not to leak a stale/partial download link (`test_compute_timeout_returns_no_partial_result_or_download`).

**Negative / edge**

- See the P0 orphaned-flow finding above: the only written recovery runbook entry for "confirmation not granted" (`docs/runbook/debugging.md` §1) documents the wrong (legacy) route and status code for the real `/app` journey's equivalent situation.
- 404 behavior for documentation routes is strict and security-correct (traversal, encoding, case, null-byte, and double-encoding attempts all 404, confirmed by the full `TestPathTraversalPrevention`/`TestAssetSecurityNegative` suites in this run), but a legitimate user who mistypes a module name or hits a stale link gets a bare Flask 404 with no "did you mean" or link back to `/docs/modules` — a missed low-cost recovery opportunity, not a defect.

### 7. No-JS boundaries and browser-deferred limitations (explicitly scoped as non-blocking)

- The `/app` workflow is enforced no-JS at the CSP layer (`CSP_APP` in `app/__init__.py` has no `script-src`, so `default-src 'none'` blocks script execution) and at the template layer (`test_app_workflow.py::test_get_app_has_accessible_criteria_modes_and_no_scripts` statically asserts no `<script>` tag and no `onload=` attribute, confirmed passing). This is a correctly enforced, test-backed boundary, not an aspirational claim.
- Docs/tutorial routes permit `script-src 'self'` for genuinely progressive enhancements (theme toggle, code-row highlight) that degrade to working CSS-only (`:target`) behavior, which this audit confirmed by source inspection of `ranking_tutorial_side_by_side.html`.
- Consistent with the Engineering Critic's audit and the task context, this audit makes **no claim** about actual browser rendering, zoom/reflow behavior, assistive-technology operation, or offline/`file:` execution. All such evidence remains deferred and non-blocking for v0.1. The static/keyboard-source assertions summarized above are real, executed, and passing, but they are not a substitute for browser execution evidence.

## Limitations of this audit

This review inspected local source, templates, routes, and CSS, and executed one focused pytest run (503 passed) through local subprocess invocation. It did not fetch or compare live upstream state. It made no browser, assistive-technology, zoom, reflow, keyboard-execution, or offline/`file:` observation; all such evidence remains deferred and non-blocking per the current project policy. It did not edit any application or documentation page and performed no Git operation of any kind, local or remote. All findings above are either (a) directly observed in source/templates, or (b) confirmed by an executed, passing, or explicitly cited local test; no finding relies on an unverified assumption about runtime behavior beyond what the cited test exercises.

## Decision rationale
