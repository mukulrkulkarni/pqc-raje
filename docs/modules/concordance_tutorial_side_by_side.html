Notation

Dimensions
  • N = total number of alternatives (objects/options being ranked)
  • C = number of criteria (attributes used for comparison)
  • B1 = number of row alternatives in the current block (subset of N)
  • B2 = number of column alternatives in the current block (subset of N)
Performance
  • g(a,j) = performance of alternative a on criterion j (higher is better for maximize criteria)
  • diff[i,k,j] = g(row_i, j) - g(col_k, j) = performance difference for pair (i,k) on criterion j
Why shape (B1,B2,C)?

For each pair (a,b) in a block of B1 rows × B2 columns, we compute the difference on each of C criteria. Example with B1=1, B2=1, C=3 (one pair, three criteria): diff = [[[d1, d2, d3]]] where d1, d2, d3 are the differences on criteria 1, 2, 3. The triple brackets reflect: outer = B1 rows, middle = B2 cols, inner = C criteria.

Output range
c_j, C ∈ [0,1] (clipped)

q=p case

Monotonicity

Scientific grounding & calibration notes

ELECTRE III context: Concordance is one of three pillars in ELECTRE III (concordance, discordance, credibility). Concordance measures the coalition of criteria supporting the hypothesis "a outranks b". It is aggregated across criteria before discordance can veto the outranking.

Partial vs global: Partial concordance c_j(a,b) measures support from a single criterion j. Global concordance C(a,b) = Σ w_j c_j(a,b) aggregates all criteria weighted by importance. The global concordance feeds into credibility computation where discordance may reduce it.

Threshold semantics: q (indifference) and p (preference) define fuzzy boundaries. When a's performance exceeds b's by more than q, there is full concordance on that criterion (c_j=1). When b exceeds a by more than p, there is no concordance (c_j=0). Between -q and -p, linear interpolation provides a smooth transition.

Maximize vs minimize: This implementation assumes higher g values are better (maximize). For minimize criteria, negate the performance values before computing diff, or invert the difference signs. The threshold semantics remain the same.

Numerical stability: When q=p (degenerate case), the interpolation denominator (p-q) is zero. The guard sets denom=1, but the piecewise conditions (diff ≥ -q and diff ≤ -p become the same test) ensure the interpolation value is never actually used. Final clip ensures output stays in [0,1] despite any floating-point accumulation.

Purpose

This module implements concordance computation for ELECTRE III multi-criteria decision analysis. Concordance quantifies the strength of the coalition of criteria supporting the outranking hypothesis "alternative a is at least as good as alternative b". It is the first of three stages: concordance → discordance → credibility.

I/O

Module-level: imports numpy. Exports two pure functions: partial_concordance (per-criterion) and global_concordance (weighted aggregation). Both operate on batched NumPy arrays for efficient block-wise computation.

Why

In ELECTRE III, concordance captures the degree to which criteria support an outranking relation. Unlike simple weighted sums, ELECTRE separates concordance (positive evidence) from discordance (veto evidence). This separation allows minority criteria with strong opposition to block an outranking even when the majority supports it.

Pitfalls

Threshold validation (0 ≤ q ≤ p) is not enforced here; it must be validated upstream via validate_thresholds. Passing p < q produces mathematically undefined results. Weight normalization (sum=1) is required for global_concordance but not enforced here; use normalize_weights.

Purpose

Computes the partial concordance c_j(a,b) for each criterion j. This is a piecewise linear function that maps performance differences to a [0,1] score indicating how strongly criterion j supports the claim "a outranks b".

I/O

  • diff — ndarray(B1,B2,C): performance differences g_j(a) - g_j(b) for B1×B2 pairs across C criteria. Assumes higher values favor a (maximize semantics).
  • q — ndarray(C): indifference thresholds per criterion. Differences ≥ -q yield full concordance.
  • p — ndarray(C): preference thresholds per criterion. Differences ≤ -p yield zero concordance.
  • Returns: ndarray(B1,B2,C) in [0,1], same shape as diff.

Why

Partial concordance implements the ELECTRE III piecewise formula: c_j=1 when a is clearly better or equivalent (diff ≥ -q), c_j=0 when b is clearly preferred (diff ≤ -p), and linear interpolation in between. This fuzzy boundary avoids knife-edge sensitivity to small measurement differences.

Pitfalls

Shape broadcasting: q and p are (C,) and broadcast against diff's last axis. Precondition 0 ≤ q ≤ p is not enforced here. When q=p, the interpolation region vanishes (binary concordance). For minimize criteria, negate diff values before calling.

Purpose

Implements the piecewise linear concordance formula. Three regions: (1) diff ≥ -q → c=1, (2) diff ≤ -p → c=0, (3) -p < diff < -q → linear interpolation c = (diff + p)/(p - q). The nested np.where applies conditions in priority order.

I/O

Internal: computes interpolated values first (vectorized across entire array), then applies piecewise conditions. Final np.clip(c, 0.0, 1.0) ensures output stays in [0,1] despite any floating-point accumulation errors.

Why

Vectorization via numpy broadcasting enables efficient batch computation. Computing c_interp for all elements first (even those that will be overwritten) is faster than conditional loops. The clip is a safety net—mathematically unnecessary if inputs are valid, but guards against floating-point edge cases.

Pitfalls

Division by (p-q): when q=p, denom=0 would cause division error. The denom guard sets denom=1 to avoid NaN; c_interp is computed but then masked by the piecewise branches (both conditions diff ≥ -q and diff ≤ -p collapse to the same test, so one of them always fires). Monotonicity: c_j is monotonically non-decreasing in diff—larger differences always yield equal or higher concordance.

Purpose

Aggregates partial concordances into the global concordance index C(a,b) = Σ w_j c_j(a,b). This weighted sum measures overall support for "a outranks b" across all criteria, weighted by criterion importance.

I/O

  • c_j — ndarray(B1,B2,C): partial concordance values from partial_concordance, all in [0,1].
  • weights — ndarray(C): criterion weights. Contract: weights ≥ 0 and sum(weights) = 1. Use normalize_weights() upstream to ensure this; not enforced in this module.
  • Returns: ndarray(B1,B2) in [0,1] if weights are normalized; may exceed 1 otherwise.

Why

einsum("ijk,k->ij", c_j, weights) is an efficient tensor contraction that sums over the criteria axis k. Equivalent to (c_j * weights).sum(axis=-1) but typically faster for large arrays. The weighted sum reflects that not all criteria are equally important in the decision.

Pitfalls

Weight normalization contract: This function does not validate weights ≥ 0 or sum(weights)=1. Negative weights produce mathematically undefined results. If weights sum to >1, C(a,b) can exceed 1 (invalid). If weights sum to <1, C(a,b) is artificially deflated. Enforcement is upstream-only: call normalize_weights() from the validate module before passing weights here.

Purpose

Documents edge cases and numerical stability guards. The division by (p-q) is guarded; the final clip ensures [0,1] bounds. These guards handle degenerate inputs without crashing, though such inputs may indicate upstream configuration errors.

I/O

  • NaN/Inf in diff: propagates to output (NumPy semantics). Validate inputs upstream if NaN-free output is required.
  • Criteria mismatch: if q, p, weights have different lengths from diff's last axis, NumPy will raise or silently broadcast incorrectly.
  • p < q: invalid configuration (precondition violation). Results are mathematically undefined; validate upstream.

Why

q=p degeneracy: when indifference equals preference threshold, the interpolation region has zero width. This is a valid "binary concordance" model (c=1 or c=0, no gradation). The denom=1 guard avoids division by zero; the piecewise conditions then select 1 or 0 based on which side of the shared threshold diff falls.

Pitfalls

Performance (qualified): For very large arrays, the vectorized implementation may be memory-bound rather than compute-bound. If memory is constrained, consider block-wise processing via compute_block. No validation here: This module assumes validate_thresholds, validate_arrays_match, and normalize_weights were called upstream. Passing invalid inputs produces undefined but non-crashing results.
